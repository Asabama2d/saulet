# Saulet — предпроектная планировка (нормы РК)

Инструмент предпроектной стадии: архитектор задаёт параметры объекта → приложение
выдаёт состав помещений с площадями и нормативным обоснованием и пузырьковую
диаграмму функциональных связей.

В базе четыре типа зданий: **дошкольные организации**, **общеобразовательные
организации**, **лечебно-профилактические организации** и **ТРЦ**.
Правила задаются в `src/data/knowledge/`; новый файл также нужно зарегистрировать
в `src/lib/knowledge/loader.ts`.

## Атлас нормативов

Раздел **«Атлас норм»** (`/norms`) содержит защищённый граф всей загруженной базы:
695 документов, 270 376 пунктов и фрагментов, 22 темы. Можно выбрать «Двери»,
«Эвакуация», «Помещения ТРЦ» или пересечение тем, искать по полным текстам,
читать пункты, таблицы и страницы исходников. Полные Markdown-тексты доступны
после открытия базы паролем или файлом `.saulet-key`.

В Git находятся только зашифрованные данные; пароль хранится отдельно. Атлас
помогает найти источники для проверки, а актуальность и применимость норм требуют
подтверждения. Порядок импорта, защита и ограничения: [docs/NORMS-ATLAS.md](docs/NORMS-ATLAS.md).

## Запуск

```bash
npm ci
npm run dev
```

Открыть <http://localhost:3000>. Бэкенда нет, проект пользователя — один JSON
(«Сохранить» / «Открыть» в шапке), текущее состояние живёт в `localStorage`.

## Надёжность проектов и проверки

- «Сохранить» скачивает JSON с параметрами, ручными правками, связями, этажами,
  закреплёнными узлами, режимом раскладки, окраской и фильтром потоков.
- При открытии проверяются структура, версия, тип здания, значения параметров,
  ручные помещения и связи. Неверный файл не меняет текущий проект. Поддерживаются
  версии 1 и 2; отсутствующие параметры получают текущие значения по умолчанию.
  Файлы больше 5 МБ отклоняются. Отличие версии базы показывается уведомлением.
- Смена назначения и открытие другого файла требуют подтверждения замены проекта.
- При ошибке хранилища появляется сообщение. Повреждённое автосохранение не
  перезаписывается: его можно скачать для восстановления. Возобновление сохранения
  заменяет его текущим проектом только после подтверждения.
- На экранах уже 1280 px параметры, планировка и сводка переключаются кнопками.
  Слои и легенда изначально свёрнуты; диалоги ограничены шириной экрана.
- Подземные этажи ТРЦ входят в раскладку и проверки размещения. CSV назначает
  уникальные номера, в том числе при пересечении исходных кодов с суффиксами.

Проверки для разработки (Node.js 22+):

```bash
npm run lint
npm run typecheck
npm test
npm run build
```

GitHub Actions запускает эти команды для pull request и изменений `main`.
Тесты охватывают все четыре типа, согласованность расчёта/диаграммы/экспорта,
подземные этажи, импорт JSON, автосохранение и уникальность номеров CSV.
Это проверки программной логики, а не подтверждение актуальности нормативной базы.
Приоритеты развития: [docs/ROADMAP.md](docs/ROADMAP.md).

## Что сделано (этапы 1–2)

**Этап 1.** Типы `src/types/knowledge.ts`, Zod-схемы и загрузчик с проверкой
ссылочной целостности, левая панель параметров детсада, движок отбора и расчёта,
таблица-экспликация с раскрывающимся audit trail, сводка, панель «Проверки».

**Этап 2.** Пузырьковая диаграмма: раскладка `d3-force` → React Flow, радиус
∝ √площади, стили узлов по статусу и функциональной группе, семь начертаний
рёбер по типу связи, интерактивная легенда, закрепление узлов перетаскиванием,
светлая и тёмная темы.

**Этап 3.** Ручная правка: создание связей протяжкой с диалогом типа и
обоснования, изменение и снятие связей, запрет снятия нормативных связей,
отступления с обязательным комментарием в отчёт, помещения по заданию на
проектирование, подсветка конфликтов на диаграмме.

**Этап 4.** Школа: параметры, восемь функциональных групп, 55 помещений с
площадями из приложений Б, Е, Ж, связи с нормативным обоснованием, проверки по
разделу 4.4 и предельная общая площадь по приложению Ж.

**Этап 5.** Слои: фильтр по функциональным потокам, окраска по санитарным зонам,
раскладка по этажам свимлейнами с назначением уровня перетаскиванием,
сворачивание функциональной группы в пузырь второго порядка.

**Этап 6.** Экспорт: XLSX (экспликация, отступления и проверки, сводка),
CSV для Revit, SVG и PNG диаграммы, JSON проекта.

Все шесть этапов задания закрыты.

## Слои (этап 5)

**Потоки.** Выберите поток в панели «Слои» — помещения и связи, к нему не
относящиеся, приглушаются. Маршрут читается в контексте объекта, а не сам по
себе, поэтому узлы не скрываются полностью.

**Зоны.** Окраска «по зонам» перекрашивает узлы в чистые, грязные и нейтральные.
Отдельная проверка ловит прямую связь чистой и грязной зоны с материальным
потоком — но только для связей, которые добавил или изменил пользователь.
Смежности базы знаний выверены по нормативу (класс с санузлом секции, зал с
раздевальными), предупреждать о них — значит утопить настоящие конфликты в шуме.

**Этажи.** Режим «по этажам» раскладывает диаграмму горизонтальными дорожками:
не назначено, затем этажи сверху вниз до подвала. Перетаскивание узла в дорожку
назначает уровень; узел не может визуально уехать в соседнюю дорожку. Свёрнутый
блок назначает уровень всем своим помещениям разом. Вместе с этажами включаются
проверки, которые до этого проверять было не на чем: `floorsAllowed`,
`floorsForbidden` и запреты `notAbove` / `notBelow` (например, санузлы над
помещениями пищеблока).

**Сворачивание блока.** Квадрат справа от группы в легенде сворачивает её в один
пузырь: радиус считается от суммарной площади блока, связи внутри блока не
рисуются. Клик по пузырю разворачивает обратно.

## Экспорт (этап 6)

| Формат | Где | Что внутри |
|---|---|---|
| XLSX | шапка → «Экспорт» | Лист «Экспликация» с колонками обоснования, редакции и дословной цитаты; лист «Отступления и проверки»; лист «Сводка» с параметрами и нормативной базой |
| CSV | шапка → «Экспорт» | `Name, Number, Department, Area, Level, Comments` — по строке на физическое помещение, номера сквозные и уникальные |
| JSON | шапка → «Экспорт» | Весь проект: параметры, ручные правки, связи, этажи, координаты узлов |
| SVG / PNG | панель диаграммы → «Картинка» | Диаграмма с легендой, штампом и дорожками этажей |

Если есть неподтверждённые позиции, лист «Экспликация» начинается с явного
предупреждения — требование п. 10.6 задания.

Диаграмма выгружается **из данных графа, а не снимком экрана**: в файле
настоящие окружности и линии, он весит около 50 КБ, открывается в Illustrator и
не зависит от текущего масштаба холста. Снимок DOM давал 5,5 МБ `foreignObject`,
который не растрировался и вешал вкладку.

## Ручная правка (этап 3)

**Связи.** Протяните от синей точки на правом краю узла к другому узлу —
откроется диалог: тип связи, сила, основание (технология или эргономика) и
обязательное обоснование. Без обоснования связь не создаётся. Клик по линии
выделяет её, `Del` снимает, двойной клик по узлу открепляет его.

**Нормативные связи снять нельзя.** Кнопка «Снять связь» для них заблокирована.
Изменить тип можно, но тогда поле «Обоснование отступления» становится
обязательным, а отступление попадает в «Проверки» строкой вида «Отступление от
нормативной связи: „Кухня с раздаточной" ↔ „Буфетная" — через коммуникацию → в
пределах блока. Норма: СП РК 3.02-110-2012\*, п. 4.4.3.12. Обоснование
автора: …». Кнопка «Как в базе» возвращает исходное значение.

**Помещения по заданию.** Кнопка «+ Помещение» на диаграмме и в экспликации.
Площадь такого помещения помечается источником «Задание на проектирование» и
входит в подтверждённую сумму под ответственность автора. На диаграмме такой
узел помечен значком «ЗД», в экспликации — карандашом для правки.

**Подсветка.** Красное штриховое кольцо на узле означает конфликт из «Проверок»
(помещение негде разместить, площадь вне диапазона, отступление). Незаполненная
или несверенная площадь кольцом не помечается — для неё есть жёлтый бейдж
в экспликации.

Всё это хранится в проекте отдельно от базы знаний, поэтому обновление
нормативной базы не стирает ручную работу.

Функциональные группы приложения М (12 индексов) сведены к восьми — ограничение
на палитру диаграммы («не более 8 цветов, различимых при дейтеранопии»).
Объединены: КНШ + У-КНШ → блок начальных классов; У-КОШ + У-КСШ → классы-кабинеты;
У-СК + У-ТМ → специализированные кабинеты и мастерские; У-ВАМ + О-РЦ + рекреации
→ общешкольные помещения. Индекс исходной группы указан в примечании помещения.

Приложение Ж работает как отдельная проверка: расчётная общая площадь
сравнивается с предельной по вместимости (интерполяция между 300, 600, 900 и
1200 обучающимися), и превышение попадает в «Проверки» с обеими цифрами.

Каждое число несёт `NormRef` с документом, пунктом, редакцией и **дословной
цитатой строки таблицы** — она видна в раскрытом расчёте строки.

Таблица К.1 задаёт площади для мощностей 50, 95, 140, 190, 280, 360, 400, 450 и
500 мест; примечание 1 к ней прямо предписывает интерполяцию для промежуточных
значений — движок так и делает и показывает это в строке расчёта.

### Что помечено «требует проверки»

`verified: false` стоит там, где извлечение из PDF было неоднозначным —
объединённые ячейки таблиц, где площадь приведена суммой нескольких помещений.

**Школа:** строка загрузочных помещений таблицы Б.12 («разгрузочная платформа»,
«загрузочная платформа», «помещение для хранения тары») в PDF слита в один блок.

**Детский сад** — таблица К.1:

- изолятор: палата и туалетная (столбцы 280–500 мест);
- физиотерапевтический кабинет (360–500 мест);
- овощной цех с предварительной обработкой;
- кабинет психолога и логопеда (500 мест);
- хозяйственная кладовая (360–500 мест);
- зал-арена, физкультурный зал, артистическая, снарядная — таблица Д.1 приводит
  их только для центров дошкольного воспитания, применимость к ОДВО общего типа
  требует решения проектировщика.

Такие строки видны с жёлтым бейджем, **не входят в подтверждённую сумму** и
собраны в панели «Проверки». Значение и подсказка, что именно сверить, показаны
в строке.

### Что осталось без числа

Технические помещения, вестибюль, коридоры, бассейн, отдельная раздаточная и
помещение уборочного инвентаря: СП их площади не нормирует. У каждого стоит
`sourceHint` с указанием, по какому документу или расчёту смежников принимать
значение.

### Как это работает в интерфейсе

- строка без числа помечена «Нет числа», заштрихована и не входит в сумму;
- число можно ввести прямо в таблице — оно получает значок «Задание»
  (`source: 'assignment'`) и входит в подтверждённую сумму под ответственность
  автора;
- в шапке всегда видно «Проверено N из M».

Итогов два: **подтверждённая** сумма и **справочная** (плюс строки с
непроверенной ссылкой). В проектную документацию выносится только первая.

Проектные допущения, явно помеченные как не-норматив: коэффициент `K = 1.20` и
высота этажа `3.3 м`.

### Расхождения внутри норматива

Инструмент их не сглаживает, а выносит в «Проверки»:

- СП РК 3.02-110-2012\*: таблица Д.1 (информационное приложение) даёт комнату
  преподавателей 6 м² при числе групп до 16, а п. 4.4.3.14 требует учительское
  помещение не менее 8 м².
- СП РК 3.02-111-2012\*: таблица Б.9 требует посадку в зрительном зале не менее
  20 % от числа обучающихся, приложение М для той же группы помещений — 30 %.
- СП РК 3.02-111-2012\*: обеденный зал по п. 4.4.2.8 считается от числа
  посадочных мест, а таблица Б.12 задаёт минимум по числу классных групп.
  Принимается большее.

## Отклонения от исходного задания

Задание требовало реализовать интерфейсы раздела 3 строго. Ниже — поля и
решения, добавленные сверх него: без них движок не связывает данные. Все они
помечены в коде комментарием `ДОПОЛНЕНИЕ`.

| Что добавлено | Зачем |
|---|---|
| `BuildingType.unitCounts` | `CountRule.per: 'group'` не с чем было сопоставить: нет способа узнать, сколько групп в объекте. Теперь единицы описаны выражениями в данных типа. |
| `RoomGroup.cellSource` | Площади ячейки яслей и дошкольной группы различаются, поэтому ячейка тиражируется **по строкам матрицы**, а не по общему числу групп. Каждая строка даёт свой экземпляр со своим `row_places`. |
| `MatrixDef` в `ParameterDef.matrix` | Контрол `group-matrix` в задании назван, но не описан. |
| `MatrixDef.rows[].tags` | Правила должны ссылаться на «все ясельные группы» без перечисления строк. Движок публикует `groupMatrix_tag_nursery_count` и т. п. |
| `AreaRule.sourceHint` | Пункт 10.5 требует у плейсхолдера комментарий, откуда брать число. Схема не пропустит площадь без нормы и без подсказки. |
| `ParameterDef.help`, `ParameterDef.section` | Текстовое пояснение, когда точного пункта нет (значок отличается от нормативного), и секции аккордеона. |
| `BuildingType.validations` | Несовместимости параметров описаны данными, а не кодом, иначе `checks.ts` пришлось бы переписывать под каждый новый тип здания. |
| `AdjacencyRule.flow` | Понадобится для фильтра по потокам (этап 5). |
| Группа `kg.comm` «Коммуникации» | В перечне раздела 11 её нет, но без вестибюля и коридоров не работают связи `via-corridor` и правило `percentOfNet`. |
| Оператор `in` | Расширен: если значение параметра — массив (`multiselect`), проверяется непустое пересечение. Отдельный оператор `contains` не вводился. |
| `AreaRule.kind: 'lookup'` | СП задаёт площади таблицами: по проектной мощности с интерполяцией (`interpolate`, таблицы К.1, Б.8, Б.12) и по категории — типу ОДВО или типу библиотеки (`match`, таблицы Е.1, Б.7). Формулами это не выражается. |
| `BuildingType.grossAreaLimit` | Приложение Ж задаёт предельную общую площадь школы по вместимости. Проверка сравнивает её с итогом расчёта. |
| `<matrix>_capacity_max` в области видимости | Учебные кабинеты считаются на полный класс (2,5 и 3,5 м²/учащегося), а не на среднюю по объекту группу. |
| Параметр `odvoType` | Типология СП (прогулочные группы / малые ОДВО / ОДВО общего типа / УВК) не совпадает с бытовой (ясли / ясли-сад / детсад), а площади ячейки зависят именно от неё. Оба параметра оставлены. |
| Свой слой рёбер вместо рёбер React Flow | Штатный рендер требует привязки к ручкам и внутреннего замера узлов. Линии идут между центрами кругов и подрезаются по известным радиусам — слой в `ViewportPortal` проще и не зависит от замеров. |
| Своя протяжка связи вместо `onConnect` | По той же причине: соединения React Flow работают только после того, как он сам замерит узлы и заполнит `handleBounds`, а размеры кругов заданы нами явно, чтобы диаграмма рисовалась сразу. Протяжка ведётся через `screenToFlowPosition` и попадание по центрам узлов. |
| Свой генератор SVG вместо снимка DOM | `html-to-image` даёт многомегабайтный `foreignObject`: он не растрируется, вешает вкладку и не правится в редакторе. Свой SVG — 50 КБ настоящих окружностей и линий. |
| Next.js 16 вместо 15 | 15 уже не ставится как `latest`; App Router и API те же. |

Ещё два расхождения по существу:

- **Итоговых сумм две, а не одна.** Задание требует не включать непроверенные
  строки в сумму. Одна цифра при пустой базе всегда была бы нулём, поэтому
  рядом показана справочная сумма — с явной подписью, что в ПД она не идёт.
- **Класс пожарной опасности не проставляется жёстко.** Ф1.1 стоит по
  умолчанию, значение редактируемое, отличие от Ф1.1 попадает в «Проверки».

## Как добавить новый тип здания

Движок не знает ни про детсады, ни про школы: он читает JSON. ЛПУ, жилые дома,
ТРЦ, паркинги добавляются файлом без правки кода.

1. Создайте `src/data/knowledge/<тип>.json` по структуре `BuildingType`
   (см. `src/types/knowledge.ts`) и зарегистрируйте его в
   `src/lib/knowledge/loader.ts` — одна строка в списке `buildingTypes`.
2. Опишите:
   - `parameters` — левая панель. Секции задаются полем `section`, матрица
     повторяемых единиц — контролом `group-matrix` с метками строк (`tags`).
   - `unitCounts` — чем считаются `CountRule.per`: сколько групп, палат,
     квартир, машино-мест. Это единственное место, где движок узнаёт «единицу»
     конкретного типа здания.
   - `groups` — функциональные группы, не более восьми цветов.
   - `rooms` — состав с `condition`, `count`, `area`, `constraints`, `flows`,
     `zone` и ссылкой на норму.
   - `adjacency` — связи с обоснованием; `basis: "norm"` требует `norm`.
   - `validations` — несовместимости параметров данными, а не кодом.
   - `grossAreaLimit` — предельная общая площадь, если норматив её задаёт.
3. Для площадей выбирайте вид правила: `fixed`, `perPlace`, `perUnit`,
   `range`, `percentOfNet`, `formula` или `lookup` (таблица норматива —
   интерполяция по числу либо выбор по условию).

Что уже переиспользуется без изменений: расчёт и audit trail, тиражирование
повторяемых ячеек, проверки этажей и зон, слои, ручная правка, все четыре
формата выгрузки. Специфика типа живёт только в JSON.

Чего в движке пока нет и что понадобится для новых типов: расчёт по нескольким
матрицам сразу (например, палаты и кабинеты в ЛПУ считаются раздельно), правила
на состав квартир и машино-мест, привязка помещения к нескольким этажам.

## Как дополнять базу

1. Открыть `src/data/knowledge/kindergarten.json`.
2. Подставить число в `area.value` (или узел в `area.lookup.points`) и заполнить
   `area.norm` точным документом, пунктом и дословной цитатой. `verified: true`
   ставить только после сверки с первоисточником.
3. Приложение не запустится, если база не прошла Zod-валидацию или проверку
   ссылочной целостности — ошибка будет с указанием пути в JSON.

Редакция документа в базе — та, что лежит в папке пользователя. В файле
СП РК 3.02-110-2012* последнее изменение — приказ КДСиЖКХ от 23.11.2018 г.
№240-НҚ. Если появится более поздняя редакция, сверить нужно все таблицы
приложений Д, Е, Ж и К.
